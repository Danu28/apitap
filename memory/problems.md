## 2026-09-03 — Unchecked runtime.lastError: message port closed before response
- Class: Meaningful-quality (console noise + masked errors; export-path false-negative possible)
- Evidence: `Unchecked runtime.lastError: The message port closed before a response was received` (Context: Unknown, empty stack — a terminated-context log). Root cause: MV3 `sendMessage` errors are unhandled at all three send sites because no callback reads `chrome.runtime.lastError`:
  1. `devtools.js:57` — `sendMessage({type:'API_CALL',...})` with NO callback; the try/catch only covers sync throws. Fires when the SW is mid-termination (SW sleeps ~30s idle) — the loudest source, can repeat during recording.
  2. `panel.js:32` — callback ignores lastError; when the SW dies mid-await (e.g., EXPORT handler awaiting the saveAs dialog, GET_SESSION awaiting restore) or DevTools closes mid-flight, `res` is undefined → resolves `{}` as success, masking real errors in toasts.
  3. `background.js:26` — broadcastUpdate callback `() => {}` ignores lastError; panel closed → no receiver.
- Why not blocking: MV3 message delivery wakes the SW (queued), so captures aren't demonstrably lost; recording works.
- Fix (4 lines, standard MV3 hygiene): consume lastError at each site — devtools: `(msg, () => void chrome.runtime.lastError)`; panel: read `void chrome.runtime.lastError` and resolve `{success:false, error:...}` when `res === undefined`; background: same `() => void chrome.runtime.lastError`. Optional follow-up: EXPORT handler can respond optimistically after queuing the download so the panel toast doesn't depend on the saveAs dialog outliving the SW.
## 2026-09-03 — Post-release verification (popup/debugger v1.1.0)
- B1 Meaningful-quality — background.js:142-150 — post-stop/clear ingestion race. `Network.loadingFinished` fires, then `getResponseBody` promise settles AFTER Stop/Clear: the `.then/.catch` unconditionally `pendingRequests.delete + ingestApiCall`, and `ingestApiCall` (line 104) does `correlator || initCorrelator()` — so after **Clear**, a fresh engine is created and a phantom call lands in the cleared session, then re-persisted. Repro sequence: request in flight → user clicks Stop or Clear quickly → phantom request appears in the just-cleared session. Fix: in both callbacks, `if (!pendingRequests.has(params.requestId)) return;` before delete+ingest (a new Map per session makes this the session guard).
- B2 Meaningful-quality — background.js restorePersistedSession (persistSession saves isRecording/recordingStartTime/engine only, never recordingTabId). After an MV3 SW restart mid-recording, restore leaves isRecording=true + recordingTabId=null → every onEvent hits the line-127 guard and is dropped: popup shows "Recording · tab ?" forever with zero capture. Fix: persist recordingTabId; on restore, if isRecording && tabId, re-attach debugger + Network.enable; on attach failure set isRecording=false + persist.
- B3 Advisory — start-window drop: requests already in flight when recording starts (between Network.enable and isRecording=true) are missed; in-flight-at-Stop requests are lost by design (no loadingFinished).
- B4 Advisory — utils/debugcapture.js decodeBase64: binary non-noise bodies (PDF/image/zip APIs) decode as UTF-8 mojibake into responseBody (harmless in export, ugly in JSON view). Store a base64Encoded flag instead.
